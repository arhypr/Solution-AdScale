# Дизайн API Gateway для DSP-интеграции

## 1. Общие требования

- Обработка до 18 000 RPS в пике (с возможностью масштабирования до 50 000).
- Добавление не более 5 мс к общей задержке (Gateway overhead минимален).
- Поддержка OpenRTB 2.5 через HTTPS.

## 2. Маршрутизация

- **Эндпоинт:** `POST /openrtb/bid`
- Gateway принимает OpenRTB-запрос, валидирует его, извлекает API ключ, преобразует во внутренний `BidRequest` (gRPC) и
  вызывает Bidding Service.
- При ответе преобразует gRPC ответ в OpenRTB response.

## 3. Аутентификация

- Используется **API Key** в заголовке `X-API-Key`.
- Gateway проверяет ключ по внутреннему хранилищу (либо в Redis, либо в базе партнёров).
- При невалидном ключе возвращается `401 Unauthorized`.

## 4. Rate Limiting

- Настраивается для каждого партнёра (по API Key).
- Ограничение: не более 1000 запросов в секунду на одного партнёра (настраивается).
- Реализуется через плагин `rate-limiting` в Kong (с использованием Redis для распределённого счётчика).
- При превышении лимита возвращается `429 Too Many Requests`.

## 5. Circuit Breaker (Автоматический размыкатель)

- Защищает Bidding Service от перегрузок.
- Настраивается таймаут (80 мс), порог ошибок (5% в течение 10 секунд).
- При срабатывании Circuit Breaker переключается в состояние **OPEN**, и Gateway возвращает дефолтный ответ (или
  кэшированную ставку) без вызова сервиса.
- Используется плагин `circuit-breaker` Kong или реализуется через Envoy.
- При частичном восстановлении переходит в **HALF-OPEN**, пропуская часть трафика для проверки.

## 6. Мониторинг времени отклика

- Gateway собирает метрики: общее время ответа, время до Bidding Service, статусы HTTP.
- Метрики экспортируются в **Prometheus** и визуализируются в **Grafana**.
- Настраиваются алерты при превышении порога latency (например, P95 > 70 мс на Gateway).

## 7. Резервные стратегии

- При недоступности Bidding Service или превышении таймаута Gateway возвращает **дефолтную ставку** (например,
  минимальную CPM) и фиксирует событие в логах.
- Кэшированные ставки могут храниться в Redis на уровне Gateway (краткосрочное кэширование для повторных запросов с тем
  же placement_id, если это допустимо по бизнес-правилам).

## 8. Схема работы Gateway

1. Получение HTTPS-запроса.
2. Аутентификация (API Key).
3. Rate Limiting.
4. Преобразование OpenRTB → внутренний gRPC.
5. Вызов Bidding Service через gRPC с таймаутом (80 мс).
6. В случае успеха – преобразование ответа и возврат.
7. В случае ошибки/таймаута – применение Circuit Breaker и возврат дефолтного ответа.
8. Логирование всех событий и отправка метрик.

## 9. Выбор технологии

- **Kong** с плагинами (или **Envoy** с фильтрами).
- Для простоты администрирования и наличия готовых плагинов выбран **Kong**.
- Kong разворачивается в Kubernetes, масштабируется горизонтально.
