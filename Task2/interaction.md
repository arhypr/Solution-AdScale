# Схема взаимодействия и выбор протоколов

## 1. Внешнее взаимодействие с DSP

- **Протокол:** OpenRTB 2.5 (стандарт IAB) через **HTTPS**.
- **Обоснование:** OpenRTB является индустриальным стандартом для RTB, все DSP-партнёры его поддерживают. HTTPS
  обеспечивает шифрование и аутентификацию (API ключи в заголовках).
- **Формат:** JSON (легко парсится, человекочитаем) — допустим для 18 000 RPS; при необходимости можно перейти на
  Protobuf, но для первого этапа JSON достаточен.
- **Требования к latency:** синхронный запрос-ответ, общий budget 80 мс (с учётом Gateway и Bidding Service).

## 2. Внутреннее взаимодействие между микросервисами

### 2.1 Ad Server → Bidding Service

- **Протокол:** **gRPC** (с Protobuf).
- **Обоснование:**
    - Высокая производительность и низкая задержка (бинарный протокол, мультиплексирование).
    - Строгая контрактная типизация (снижает ошибки интеграции).
    - Поддержка потоковой передачи (не используется, но возможна для будущих расширений).
    - Лёгкая интеграция с трейсингом (Jaeger, OpenTelemetry).
- **Альтернативы:** REST (HTTP/JSON) — медленнее из-за парсинга и текстового формата, не подходит для жестких SLA.

### 2.2 Bidding Service → другие сервисы (асинхронно)

- **Протокол:** **Apache Kafka**.
- **Обоснование:**
    - Асинхронная, надёжная доставка событий с возможностью воспроизведения.
    - Высокая пропускная способность (миллионы событий/сек).
    - Поддержка consumer groups для масштабирования обработчиков (Financial Service, Statistics, Analytics).
    - Развязывает критический путь аукциона от некритичных операций (запись в БД, аналитика).
- **События:** `bid_win`, `bid_loss`, `impression`, `click`, `budget_update`.

### 2.3 UI / Advertiser Dashboard

- **Протокол:** **REST (HTTP/JSON)**.
- **Обоснование:** простота интеграции с фронтендом, поддержка браузеров, кэширование, стандартные методы CRUD.

## 3. API Gateway

**Необходим** для:

- Единой точки входа для внешних DSP-запросов (маршрутизация на Bidding Service).
- Аутентификации (проверка API ключей).
- Rate Limiting (защита от DDoS и превышения лимитов).
- Circuit Breaker (изоляция сбоев Bidding Service).
- Мониторинга и логирования входящих запросов.
- **Выбор:** **Kong** (Open Source, расширяемый плагинами, поддержка gRPC-транскодирования) или **Envoy** (более
  низкоуровневый, хорошо интегрируется с сервис-мешем). Учитывая бюджет и простоту, рекомендуется **Kong** с плагинами (
  rate-limiting, jwt, circuit-breaker).

## 4. Резюме по протоколам

| Взаимодействие              | Протокол        | Обоснование                                 |
|-----------------------------|-----------------|---------------------------------------------|
| DSP → AdScale               | OpenRTB (HTTPS) | Индустриальный стандарт                     |
| Ad Server → Bidding Service | gRPC            | Низкая задержка, строгий контракт           |
| Bidding Service → Kafka     | Kafka Protocol  | Асинхронность, надёжность, масштабируемость |
| UI → Backend                | REST (HTTP)     | Удобство для фронтенда                      |
| Bidding Service → Redis     | Redis Protocol  | Кэширование in-memory для скорости          |
