# AS-IS анализ текущей архитектуры AdScale

## 1. Общая характеристика
AdScale представляет собой **гибридный монолит** (C++/Go/Python/Node.js), развёрнутый на одном production-кластере без контейнеризации. Взаимодействие между компонентами — синхронное (internal calls). Единая инстанция PostgreSQL используется для всех операций (OLTP, аналитика, финансы, события).

**Ключевые метрики (пик):**
- RPS: 15 000
- P95 latency: 110–120 ms (при целевом ≤ 100 ms)
- Отсутствие запаса производительности, периодические деградации в часы пик.

## 3. Выявленные узкие места и точки отказа

| Компонент | Проблема | Влияние на масштабирование | Влияние на latency |
|-----------|----------|----------------------------|---------------------|
| **Ad Server** | Принимает все bid requests, синхронно вызывает Auction Engine | Нет горизонтального масштабирования; бутылочное горлышко на входе | Добавляет накладные расходы на маршрутизацию и сериализацию |
| **Auction Engine** | Синхронные JDBC-вызовы к PostgreSQL в hot path | Каждый запрос ждёт ответа от БД, что ограничивает пропускную способность | Основной вклад в P95 (задержки БД + вычисления) |
| **Statistics Service** | Прямая запись кликов/показов в PostgreSQL без буферизации | Высокая write-нагрузка конкурирует с транзакционными запросами; рост времени записи | Увеличивает общую нагрузку на БД, вызывая блокировки и рост latency других сервисов |
| **Analytics Service** | Тяжёлые SQL-запросы напрямую к production-БД (без read-replica) | Долгие запросы блокируют ресурсы, снижая доступность для критичных операций | Рост блокировок приводит к таймаутам Auction Engine |
| **PostgreSQL** | Единая инстанция, нет реплик, нет шардирования | SPOF; невозможно масштабировать чтение/запись независимо | Конкуренция между OLTP и аналитикой вызывает непредсказуемые задержки |
| **Отсутствие кэша** | Все запросы к БД проходят синхронно, даже для повторяющихся данных (кампании, ставки) | Каждый RPS = запрос к БД, линейная зависимость пропускной способности от БД | Добавляет сетевые задержки и накладные расходы на парсинг |
| **Отсутствие очередей** | Асинхронные задачи (статистика, аналитика) выполняются синхронно | При пике нагрузка на запись перегружает БД и блокирует критический путь | Прямая запись увеличивает общее время ответа |
| **Ручной деплой** | Отсутствие CI/CD, контейнеризации, оркестрации | Любое изменение требует ручного вмешательства, время восстановления (MTTR) высокое | Не влияет напрямую, но увеличивает риск длительных простоев |

## 4. Риски при сохранении текущей архитектуры
- **Нарушение SLA** с новым DSP-партнёром (требование ≤80 ms, а текущий P95 уже 120 ms).
- **Финансовые штрафы** за деградацию latency и простои.
- **Потеря аукционов** — при таймаутах ответ не отправляется, площадка уходит к конкурентам.
- **Репутационные потери** и отток текущих клиентов.
- **Невозможность обслужить рост** до 18 000 RPS через 3 месяца и 50 000 RPS через год.

## 5. Выводы
Текущая архитектура непригодна для масштабирования и достижения требуемых SLA. Необходима **немедленная эволюция**, начинающаяся с самых критичных компонентов (Auction Engine, работа с БД и статистика) с использованием паттерна **Strangler Fig**.
