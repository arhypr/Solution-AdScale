# ADR-001: Стратегия эволюции архитектуры

**Дата:** 2026-08-27

**Статус:** Accepted

## Контекст

AdScale — SaaS-платформа для цифровой рекламы, работающая на рынке несколько лет. Текущая система представляет собой гибридный монолит (C++/Go/Python/Node.js) с единой PostgreSQL, без кэширования и очередей, развёрнутая вручную на одном кластере. Пиковая нагрузка — 15 000 RPS, P95 latency 110–120 мс при целевом ≤100 мс. Система работает на пределе, отсутствует запас производительности.

Ключевые архитектурные драйверы:
- Интеграция с новой DSP-площадкой требует роста до 18 000 RPS через 3 месяца и до 50 000 RPS через год.
- Строгие SLA: P95 latency ≤80 мс для аукциона, стабильность, отсутствие простоев.
- Бюджет ограничен, нельзя переписать систему полностью; нужна постепенная эволюция с сохранением непрерывности бизнеса.
- Команда: 35 человек, нет выделенных SRE, техписателя, бизнес-аналитика.

Рассматривались три альтернативы:

1. **Оставить монолит** – оптимизировать код, индексы, настройки БД.
   - Плюсы: минимальные изменения, быстрый старт.
   - Минусы: не решает проблем масштабирования, SPOF, конкуренции за ресурсы, высокой latency.

2. **Полная переработка в микросервисы (Big Bang)**.
   - Плюсы: современная архитектура, гибкость.
   - Минусы: огромные затраты, высокий риск срыва сроков, остановка бизнеса на время перехода, требует сложной инфраструктуры (Kubernetes, сервис-меш), нереалистично за 3 месяца.

3. **Постепенное замещение частей монолита (Strangler Fig Pattern)**.
   - Плюсы: минимизация рисков, управляемый бюджет, обучение команды, обратная совместимость, возможность корректировки плана.
   - Минусы: требует дисциплины в разделении трафика между старым и новым кодом, нужен API Gateway для маршрутизации, усложняется мониторинг.

## Решение

Выбрана стратегия **Strangler Fig Pattern** – постепенное выделение наиболее критичных компонентов в микросервисы с сохранением монолита как временного шлюза. Первым приоритетом выделяется **Bidding Service** (аукцион), затем Statistics, Analytics, Financial, Ad Server. На каждом этапе новый сервис принимает часть трафика через API Gateway, остальное обрабатывается монолитом. Внедряются контейнеризация (Docker) и оркестрация (Kubernetes) по мере роста.

## Последствия

**Положительные:**
- Бизнес остаётся работоспособным на всех этапах миграции.
- Ресурсы направляются на самые узкие места (сначала аукцион), что даёт быстрый эффект по latency.
- Команда постепенно осваивает микросервисы, CI/CD, Kubernetes без шоковой терапии.
- Гибкость: приоритеты можно менять на основе результатов каждого этапа.

**Отрицательные:**
- Усложняется архитектура – появляются распределённые транзакции, увеличивается сетевое взаимодействие.
- Требуется внедрение API Gateway (Kong/Envoy) и системы распределённой трассировки (Jaeger).
- DevOps-нагрузка растёт: нужно поддерживать и монолит, и новые сервисы.
- Некоторые модули монолита останутся на старых технологиях, что может создать технический долг.

**Риски:**
- При неправильной приоритизации может не хватить времени на критичные компоненты к моменту подключения DSP (3 месяца).
- Сложность маршрутизации трафика может привести к ошибкам (часть запросов уходит в неправильный сервис).
- Если команда не соблюдает границы модулей при выделении, могут возникнуть регрессии в монолите.
