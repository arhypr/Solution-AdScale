# ADR-002: Выделение сервиса ставок (Bidding Service) как первого приоритета

**Дата:** 2026-08-29

**Статус:** Accepted

## Контекст

Auction Engine – наиболее критичный по latency компонент, находящийся на горячем пути каждого bid request. В текущей архитектуре он синхронно обращается к PostgreSQL (чтение кампаний, ставок, таргетинга) через JDBC, что создаёт основную задержку (P95 уже 110–120 мс). При росте RPS до 18 000 этот компонент станет непреодолимым узким местом, а при 50 000 RPS – полностью неработоспособным.

Ключевые архитектурные драйверы:
- Новый DSP-партнёр требует P95 latency ≤80 мс для всего аукциона.
- Невозможно переписать весь монолит за 3 месяца, нужно сфокусироваться на самом узком месте.
- Бюджет ограничен, но выделение одного сервиса и внедрение кэша (Redis) – затраты приемлемы.

Рассматривались три альтернативы:

1. **Оптимизация текущего Auction Engine внутри монолита** – добавление индексов, настройка пула соединений, кэширование в памяти процесса.
   - Плюсы: быстро, без изменения архитектуры.
   - Минусы: ограниченный эффект, не решает проблему масштабирования, память процесса ограничена, нет изоляции от других модулей.

2. **Выделение Auction Engine в отдельный микросервис с Redis для кэширования**.
   - Плюсы: изоляция hot path, независимое масштабирование, снижение latency за счёт in-memory кэша, возможность использовать C++/Go для максимальной производительности.
   - Минусы: требует внедрения Redis Cluster, асинхронного обновления кэша, изменения интерфейсов (gRPC), дополнительного деплоя.

3. **Выделение и переписывание на более быстром языке (Rust/C++) с собственным in-memory хранилищем**.
   - Плюсы: максимальная производительность.
   - Минусы: слишком долго и дорого для первого этапа, высокий риск, не даёт выигрыша в сроках.

## Решение

Выбран вариант **2**. Auction Engine выделяется в отдельный микросервис (Bidding Service) на C++ (для вычислений) и Go (для управления). Для кэширования кампаний, ставок и таргетинга внедряется **Redis Cluster**. Кэш обновляется асинхронно через события из Kafka при изменении кампаний. Взаимодействие с Ad Server – по gRPC, с Delivery Service – также асинхронно через Kafka для отправки результатов аукциона.

## Последствия

**Положительные:**
- Резкое снижение latency – чтение из Redis вместо PostgreSQL сокращает время с 5–10 мс до <1 мс.
- Bidding Service можно масштабировать горизонтально независимо от других компонентов.
- Изоляция критического пути – сбои в других модулях не влияют на аукцион.
- Создаётся основа для дальнейшей декомпозиции – другие сервисы смогут использовать аналогичный подход.

**Отрицательные:**
- Увеличивается инфраструктурная сложность – нужны Redis Cluster, Kafka, настройка мониторинга.
- Изменяется интерфейс – внутренние вызовы заменяются сетевыми (gRPC), добавляется задержка сети (но она компенсируется кэшем).
- Требуется обеспечить консистентность кэша с БД – нужна надёжная инвалидация и механизм обновления.
- Увеличивается нагрузка на DevOps – нужно разворачивать и поддерживать два новых компонента.

**Риски:**
- При сбое Redis или его переполнении Bidding Service может упасть, что приведёт к полной недоступности аукциона (нужен fallback – чтение из PostgreSQL или дефолтные ставки).
- Асинхронное обновление кэша может привести к использованию устаревших данных (допустимо до 5 минут, но для бюджета критично – нужен короткий TTL).
- Если нагрузка на Redis вырастет непредсказуемо, может потребоваться увеличение кластера, что занимает время.
