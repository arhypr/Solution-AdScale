# Целевая архитектура (TO-BE) через год

## 1. Принципы целевой архитектуры
1. **Эволюционность** — постепенная замена частей монолита на микросервисы (Strangler Fig).
2. **Разделение критических и некритичных потоков** — hot path (аукцион) изолирован от аналитики и статистики.
3. **Асинхронность** — все не-блокирующие операции (сбор событий, аналитика) вынесены в очереди.
4. **Горизонтальное масштабирование** — каждый микросервис может быть масштабирован независимо.
5. **Отказоустойчивость** — устранение SPOF, репликация БД, резервирование.
6. **Наблюдаемость** — сбор метрик, распределённая трассировка, централизованное логирование.

## 2. Ключевые изменения

| Компонент | AS-IS | TO-BE |
|-----------|-------|-------|
| **Auction Engine** | Внутри монолита, синхронные вызовы к БД | Выделен в отдельный микросервис на C++/Go; использует **локальный кэш** (Redis) для ставок/кампаний; асинхронное обновление кэша через события |
| **Статистика** | Прямая запись в PostgreSQL | Через **Kafka** → потоковая обработка (Flink/Spark) → запись в отдельный **ClickHouse** для событий |
| **Аналитика** | Тяжёлые запросы к production-БД | Отдельный **аналитический микросервис**, работающий с **read-replica** PostgreSQL и витринами данных |
| **База данных** | Одна PostgreSQL инстанция | **Primary** для OLTP, **read-replicas** для аналитики, **шардирование** по клиентам (в перспективе), **репликация** для HA |
| **Кэш** | Отсутствует | **Redis Cluster** — для кэширования кампаний, ставок, таргетинговых данных; снижение нагрузки на БД |
| **Очереди** | Отсутствуют | **Apache Kafka** — для событий (показы, клики), метрик, асинхронных задач |
| **API Gateway** | Нет | **Gateway** (Kong/Envoy) для маршрутизации, аутентификации, rate limiting, агрегации |
| **Деплой** | Вручную | **Kubernetes** + Helm, CI/CD (GitLab/Jenkins), автоматическое масштабирование (HPA) |
| **Инфраструктура** | Один кластер | **Мультирегиональное** развёртывание (active-active или active-passive) для отказоустойчивости |

## 4. Пошаговый план миграции (поэтапно)
1. **Этап 0 (подготовка):** внедрение CI/CD, контейнеризация текущего монолита, развёртывание в Kubernetes (без изменения логики).
2. **Этап 1 (3 месяца):** выделение **Auction Engine** в микросервис; внедрение Redis для кэширования; настройка Kafka для событий статистики; добавление read-replica.
3. **Этап 2 (6 месяцев):** выделение **Statistics Service** и **Analytics Service**; перенос аналитики на read-replica; внедрение API Gateway.
4. **Этап 3 (9 месяцев):** выделение **Financial Service** и **Ad Server**; шардирование БД; внедрение потоковой обработки.
5. **Этап 4 (12 месяцев):** полная декомпозиция, мультирегиональность, достижение 50 000 RPS, SLA 99.9%.

## 5. Ожидаемые результаты
- **P95 latency** ≤ 80 мс (аукцион), ≤ 100 мс (общая система).
- **Пропускная способность** ≥ 50 000 RPS.
- **Доступность** 99.9%.
- **Возможность независимого масштабирования** каждого сервиса.
- **Устойчивость к пиковым нагрузкам** за счёт буферизации и кэширования.
