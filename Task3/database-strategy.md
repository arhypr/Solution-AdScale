# Стратегия баз данных для каждого сервиса (Database per Service)

В микросервисной архитектуре каждый сервис владеет собственной базой данных (или кэшем), чтобы обеспечить слабую
связанность, независимое масштабирование и изоляцию отказов. Ниже приведена таблица со всеми сервисами целевого
состояния (TO-BE), выбором СУБД и детальным обоснованием.

| Сервис                                     | Тип базы данных                                   | Обоснование                                                                                                                                                                                                                                                                                                                                                                                              |
|--------------------------------------------|---------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Ad Server**                              | **Redis** (кэш сессий и таргетинга)               | Ad Server принимает bid requests, определяет пользователя и передаёт запрос в Bidding Service. Он не хранит постоянные данные, но использует Redis для быстрого чтения профилей пользователей, сессий и таргетинговых атрибутов. Это снижает latency на входе.                                                                                                                                           |
| **Bidding Service** (сервис ставок)        | **PostgreSQL** (источник) + **Redis** (кэш)       | PostgreSQL – надёжная реляционная СУБД для хранения ставок и кампаний, обеспечивающая ACID-транзакции при обновлении данных через Campaign Service. Однако в горячем пути аукциона (SLA ≤80 мс) используется Redis Cluster для кэширования кампаний, ставок и таргетинга. Redis обеспечивает микросекундные задержки чтения, что критично для RTB. Данные обновляются асинхронно через события из Kafka. |
| **Campaign Service** (сервис кампаний)     | **PostgreSQL**                                    | Реляционная БД с поддержкой сложных запросов, транзакций и внешних ключей для управления кампаниями, таргетингом, бюджетами и ставками. Является источником истины для всех данных, связанных с рекламными кампаниями. Используется Advertiser Dashboard для CRUD-операций.                                                                                                                              |
| **Delivery Service** (сервис доставки)     | **Redis** (кэш разметки)                          | Формирует HTML/JS-разметку баннеров. Не хранит постоянные данные; использует Redis для кэширования готовых шаблонов и метаданных креативов, чтобы ускорить ответ и снизить нагрузку на внешние хранилища (S3/CDN).                                                                                                                                                                                       |
| **Statistics Service** (сервис статистики) | **ClickHouse**                                    | Колоночная СУБД, оптимизированная для высокоскоростной вставки (миллионы событий/сек) и агрегатных запросов. Поддерживает партиционирование и репликацию, что критично для масштабирования при 50 000+ событий/сек. Хранит показы, клики, конверсии и метрики аукционов.                                                                                                                                 |
| **Analytics Service** (сервис аналитики)   | **PostgreSQL (read replica)** + **ClickHouse**    | Гибридный подход: для отчётов по кампаниям (OLTP-данные) использует read replica основной БД (не нагружая master), для событийной аналитики (графики, воронки) – ClickHouse. Это позволяет строить смешанные отчёты, объединяя данные из разных источников на уровне приложения.                                                                                                                         |
| **Financial Service** (сервис финансов)    | **PostgreSQL** (кластер с синхронной репликацией) | Требуется строгая согласованность (ACID) для финансовых транзакций (списания, пополнения, балансы). Используется кластер с синхронной репликой (RPO ≈ 0) и автоматическим failover (RTO < 1 мин). Безопасность и надёжность – приоритет.                                                                                                                                                                 |
| **Advertiser Dashboard** (UI)              | **Отсутствует собственная БД**                    | Веб-интерфейс для рекламодателей. Не хранит данные самостоятельно, а обращается к Campaign Service, Analytics Service и Financial Service через API. Может использовать Redis для кэширования сессий пользователей и часто запрашиваемых отчётов (для ускорения UI).                                                                                                                                     |

## Дополнительные пояснения

- **Разделение ответственности:** Campaign Service является единственным источником правды для кампаний и ставок.
  Bidding Service использует кэш, но при его отсутствии может обратиться напрямую к PostgreSQL (fallback).
- **Выбор ClickHouse для статистики** обусловлен необходимостью обрабатывать огромные потоки событий с минимальной
  задержкой вставки и быстрыми агрегациями (группировки, оконные функции). PostgreSQL не справляется с такой
  write-нагрузкой без серьёзных компромиссов.
- **Redis для Ad Server и Delivery Service** используется как временное хранилище с TTL, что обеспечивает высокую
  производительность без необходимости разворачивания полноценных БД.
- **Отказоустойчивость финансовой БД** достигается за счёт синхронной репликации и регулярного бэкапа WAL.
