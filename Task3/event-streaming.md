# Архитектура потоковой обработки данных (Kafka)

## 1. Топики Kafka

| Топик              | Содержание                                          | Ключ          | Партиции | Retention |
|--------------------|-----------------------------------------------------|---------------|----------|-----------|
| `bid-wins`         | События выигранных аукционов (win)                  | `campaign_id` | 10       | 7 дней    |
| `bid-losses`       | События проигранных аукционов (loss)                | `campaign_id` | 10       | 7 дней    |
| `impressions`      | События показов баннеров                            | `campaign_id` | 20       | 7 дней    |
| `clicks`           | События кликов                                      | `campaign_id` | 20       | 7 дней    |
| `budget-updates`   | Обновления бюджета (списания, пополнения)           | `campaign_id` | 10       | 30 дней   |
| `campaign-updates` | Изменения в кампаниях (создание, обновление, пауза) | `campaign_id` | 10       | 30 дней   |

## 2. Схема событий: Avro вместо JSON

**Почему Avro?**

| Критерий                                 | Avro                                                                                         | JSON                                                            |
|------------------------------------------|----------------------------------------------------------------------------------------------|-----------------------------------------------------------------|
| **Размер сообщения**                     | Компактный бинарный формат, экономия до 50–70% объёма по сравнению с JSON.                   | Текстовый, избыточный (ключи полей повторяются).                |
| **Скорость сериализации/десериализации** | Высокая, без динамического парсинга, работает с байтовыми массивами.                         | Медленнее из-за парсинга строк и рефлексии.                     |
| **Схема (типизация)**                    | Строгая схема (определяется в .avsc), обеспечивает контракт между продюсерами и консюмерами. | Отсутствует; возможны ошибки из-за несоответствия полей.        |
| **Эволюция схемы**                       | Поддерживается совместимость (add/remove поля с default значениями) через Schema Registry.   | Нет встроенной поддержки; требуется ручное управление версиями. |
| **Валидация**                            | Автоматическая валидация при сериализации/десериализации.                                    | Не выполняется, ошибки проявляются позже.                       |
| **Интеграция с Kafka**                   | Нативная поддержка (Kafka Avro Serde), интеграция с Schema Registry.                         | Используется StringSerializer, но без контроля версий.          |
| **Языковая поддержка**                   | Широкая (Java, Python, Go, C++, etc.)                                                        | Ещё шире, но теряет преимущества типизации.                     |

**Вывод:** Для высоконагруженной системы (18 000+ RPS, миллионы событий в день) Avro даёт:

- Снижение сетевого трафика и нагрузки на диски (хранение).
- Ускорение обработки (меньше времени на парсинг).
- Гарантию корректности данных благодаря схеме (особенно критично для финансовых событий).
- Простоту управления версиями — новые поля добавляются без остановки потребителей.

## 3. Группы потребителей

| Группа               | Потребляемые топики                 | Назначение                            |
|----------------------|-------------------------------------|---------------------------------------|
| `financial-service`  | `bid-wins`, `budget-updates`        | Списание средств, обновление балансов |
| `statistics-service` | `impressions`, `clicks`, `bid-wins` | Запись в ClickHouse событий           |
| `analytics-service`  | `impressions`, `clicks`             | Построение витрин данных и отчётов    |
| `bidding-service`    | `campaign-updates`                  | Обновление кэша кампаний              |
| `monitoring`         | Все топики                          | Сбор метрик и алертов                 |

## 4. Политика хранения

- Retention: 7 дней для событий (показы, клики, ставки) – достаточно для агрегации и отчётов.
- Для `budget-updates` – 30 дней (финансовые аудиты).
- Используется компактное хранение (log compaction) для топиков с ключами (campaign-updates, budget-updates) –
  сохраняется последнее состояние.

## 5. Производство событий

- **Bidding Service** отправляет `bid-wins` и `bid-losses` после каждого аукциона.
- **Delivery Service** отправляет `impressions` и `clicks` по факту показа/клика.
- **Campaign Service** отправляет `campaign-updates` при изменении кампании.
- **Financial Service** отправляет `budget-updates` после списания или пополнения.

## 6. Гарантии доставки

- **Exactly-once** для финансовых операций (через идемпотентных продюсеров и транзакционные консюмеры).
- **At-least-once** для статистики (допускаются дубли, которые обрабатываются идемпотентно на стороне ClickHouse).
- Для обеспечения порядка событий в рамках одной кампании используется ключ `campaign_id` → все события по кампании
  попадают в одну партицию.

## 7. Мониторинг Kafka

- Отслеживание lag потребителей в Prometheus.
- Автоматическое увеличение числа партиций при росте нагрузки.
- Алерты при превышении порога лага (> 1000 сообщений).
