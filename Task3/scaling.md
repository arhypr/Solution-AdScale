# Стратегия масштабирования баз данных

## 1. Репликация Master-Slave (Master-Replica)

**Применяется для сервисов:** Campaign (PostgreSQL), Financial (PostgreSQL), Bidding (PostgreSQL).

- **Master** – принимает все операции записи (INSERT, UPDATE, DELETE).
- **Slave(s)** – реплики, обслуживающие запросы на чтение (для Campaign Service – чтение кампаний для Advertiser
  Dashboard; для Financial – чтение балансов в отчётах).

**Обоснование:** разгрузка master от read-нагрузки, повышение отказоустойчивости (автоматический failover при сбое
master). Для Financial Service может быть настроена синхронная репликация для минимизации потерь данных.

## 2. Шардирование (Sharding)

**Применяется для:** Campaign Service (PostgreSQL) и Financial Service (PostgreSQL) при росте объёмов данных.

- **Ключ шардирования:** `advertiser_id` (или `campaign_id` для кампаний, `user_id` для финансов).
- **Способ:** горизонтальное шардирование на основе хеша (например, `advertiser_id % N`). Используется middleware (
  например, Citus для PostgreSQL) или прикладной уровень.
- **Обоснование:** данные разных рекламодателей не пересекаются, что позволяет изолировать нагрузку и масштабировать
  хранилище линейно.

**Для Bidding Service** шардирование не требуется, так как данные кэшируются в Redis, а Postgres служит только для
записи и редких чтений.

## 3. Read Replicas для сервиса аналитики

**Сервис аналитики** использует **read replica** PostgreSQL и отдельный ClickHouse кластер.

- Read replica PostgreSQL – для отчётов по кампаниям (внешние ключи, метаданные).
- ClickHouse – для событийной аналитики (показы, клики, конверсии). ClickHouse масштабируется горизонтально через
  шардирование и репликацию (реплики для HA).

**Обоснование:** аналитические запросы не должны влиять на производительность primary БД, отвечающей за OLTP-операции.

## 4. CQRS (Command Query Responsibility Segregation)

**Применяется:** для Campaign Service и Financial Service.

- **Командная сторона (Command):** запись в primary БД (Master).
- **Запросная сторона (Query):** чтение с read replicas (или из кэша Redis для частых запросов).
- **Обоснование:** позволяет независимо масштабировать чтение и запись, а также оптимизировать модели данных для разных
  сценариев (например, денормализованные представления для отчётов).

**Для Bidding Service** CQRS реализован через Redis (кэш) – запись обновляется асинхронно через события, а чтение идет
из Redis.

## 5. Масштабирование ClickHouse

- **Шардирование** по дате (для событий) с использованием партиционирования.
- **Реплики** для отказоустойчивости.
- **Масштабирование:** добавление узлов в кластер без остановки.

## 6. Резюме по стратегиям

| Сервис                  | Репликация                                    | Шардирование           | Read replicas          | CQRS                      |
|-------------------------|-----------------------------------------------|------------------------|------------------------|---------------------------|
| Campaign                | Master-Slave                                  | Да (по advertiser_id)  | Да                     | Да                        |
| Financial               | Master-Slave (синхр.)                         | Да (по user_id)        | Да                     | Да                        |
| Bidding                 | Master-Slave (асинхр.)                        | Нет (малый объём)      | Нет (использует Redis) | Да (Redis как кэш)        |
| Statistics (ClickHouse) | Репликация таблиц                             | Да (по дате/партициям) | Нет (сам кластер)      | Нет (вставка+чтение одно) |
| Analytics               | Использует read replica Campaign и ClickHouse | –                      | Да                     | Нет (гибридный)           |
