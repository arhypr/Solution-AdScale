# Стратегия кэширования

## 1. Что кэшировать?

| Данные                              | Сервис                     | Причина                                                 |
|-------------------------------------|----------------------------|---------------------------------------------------------|
| Кампании (активные)                 | Bidding Service            | Часто читаются в горячем пути аукциона. Редко меняются. |
| Ставки (bids) для каждого placement | Bidding Service            | Используются для выбора победителя.                     |
| Таргетинговые условия               | Bidding Service            | Фильтрация кандидатов.                                  |
| Бюджеты (остаток)                   | Bidding Service            | Для проверки лимитов перед ставкой.                     |
| Разметка баннеров (HTML/JS)         | Delivery Service           | Повторное использование для частых показов.             |
| Сессии пользователей                | Ad Server (для таргетинга) | Временные данные для определения пользователя.          |

## 2. Технология и размещение

- **Redis Cluster** – распределённое in-memory хранилище.
- Размещается в том же availability zone, что и Bidding Service для минимизации сетевой задержки (< 1 мс).
- Для Campaign и Financial Service кэш может использоваться опционально для снижения нагрузки на БД.

## 3. TTL (Time-To-Live)

| Тип данных                  | TTL      | Обоснование                                                           |
|-----------------------------|----------|-----------------------------------------------------------------------|
| Кампании, ставки, таргетинг | 5 минут  | Изменения нечасты, допустима небольшая задержка обновления.           |
| Бюджеты (остаток)           | 1 минута | Бюджет меняется часто (при каждой ставке); короткий TTL для точности. |
| Разметка баннеров           | 1 час    | Редко меняется, но может быть обновлена.                              |
| Сессии пользователей        | 30 минут | Стандартный TTL для сессий.                                           |

## 4. Стратегия инвалидации

- **Инвалидация по событиям:** при изменении кампании отправляется событие в Kafka, которое потребляется Bidding Service
  и обновляет/удаляет соответствующий ключ в Redis.
- **Инвалидация по TTL** – автоматическое удаление по истечении времени.
- **Lazy инвалидация:** при чтении проверяется версия данных (можно хранить version number) – если версия не совпадает с
  БД, кэш обновляется.

## 5. Прогрев кэша (Cache Warming)

- **При старте сервиса:** Bidding Service загружает все активные кампании и ставки в Redis.
- **Периодический прогрев:** каждые 5 минут фоновый процесс проверяет актуальность кэша и подгружает недостающие данные.
- **При обновлении через события:** сразу обновляем кэш после получения события.
- **Для новых кампаний:** при создании кампании через Dashboard отправляется событие, инициирующее немедленное
  добавление в Redis.

## 6. Управление размером кэша и политики вытеснения

Redis Cluster настраивается следующими параметрами:

| Параметр            | Значение               | Обоснование                                                                                                                                                      |
|---------------------|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `maxmemory`         | 20 ГБ (на каждый узел) | Обеспечивает хранение всех активных кампаний (оценка: ~100 000 кампаний × 10 КБ = 1 ГБ, ставки ~10 млн записей × 200 байт = 2 ГБ, таргетинг ~5 ГБ, запас 12 ГБ). |
| `maxmemory-policy`  | `allkeys-lru`          | При достижении лимита удаляются наименее используемые ключи. Это предпочтительно, так как старые/неактивные кампании вытесняются.                                |
| `maxmemory-samples` | 5                      | Стандартное значение для точности LRU.                                                                                                                           |
| `activerehashing`   | yes                    | Ускоряет перехеширование, снижая задержки.                                                                                                                       |

**Дополнительные ограничения:**

- Для ключей с сессиями используется отдельная БД (или отдельный префикс) с политикой `volatile-lru` (удаляются только
  ключи с TTL).
- Мониторинг использования памяти через `INFO memory` и алерты при достижении 80% от лимита.

**Обновление кэша при переполнении:**

- При достижении `maxmemory` Redis автоматически удаляет ключи по политике LRU. Это позволяет избежать отказа в записи.
- Если критичные данные (например, бюджеты) могут быть вытеснены, они имеют более короткий TTL и часто обновляются, что
  снижает риск использования устаревших данных.
- Дополнительно настроен `eviction-threshold` на уровне приложения: если кэш заполнен > 80%, инициируется принудительный
  сброс старых кампаний, завершившихся более 7 дней назад (через фоновую задачу).

## 7. Защита от кэш-пробивания (cache stampede)

- Используются блокировки (setnx) при обновлении тяжёлых данных (например, загрузка всех кампаний при старте).
- При промахе кэша и одновременных множественных запросах, только один поток инициирует загрузку из БД, остальные
  ожидают (через распределённую блокировку Redis).
